### Pooling, time bounds and portability

Session pooling preserves the current pg session settings and migration advisory-lock semantics, avoiding a transaction-pool adapter rewrite or new local pooler infrastructure for two health endpoints. Supabase recommends transaction pooling for general serverless scaling; the explicit tradeoff here is that each active session can occupy a backend connection. Restrict the prototype to low traffic, a small application pool and platform access controls, and verify the existing project's connection budget before deployment. Transaction pooling is a later scaling decision, not a second implementation in this plan. Preserve fresh queries, full ordered migration-state checks, server timeout and client destruction on deadline/cancellation.

Preserve local pool max 4; use hosted max 2, min 0 and idle timeout 1000ms, with immediate failure when both slots are occupied. This accommodates Fluid concurrent requests without an unbounded per-instance pool. Keep acquisition 1000ms, statement 1000ms, client query 1500ms and overall readiness 3000ms; no retries or stale-success cache. Prove two-slot behavior locally and actual Session-pool timeout/cleanup during authorized database validation. Multiple warm instances multiply connections; confirm budget and monitor the limited prototype before wider use, rather than silently increasing limits.

Create one Nest application and pg Pool per warm function instance, never per request. Add pinned `@vercel/functions` 3.10.4 only under a future install/lock lease, attaching `attachDatabasePool(pool)` once via the platform composition helper when running on Vercel. Preserve local signal/module shutdown; serverless cleanup must not depend solely on process signals. Never call `pool.end()` after each request. Verify abort propagation using Vercel's supported request-cancellation configuration and the existing request lifecycle; do not assume local disconnect tests prove platform cancellation.

## Health and bounded failure

GET /health/live: 200 {status:ok} independently of DB. GET /health/ready: 200 {status:ready,database:up,migrations:current} only after a fresh real query verifying required migration state. Otherwise 503 with contract-defined degraded body and safe reason database_unavailable, database_timeout or migrations_pending. No hosts, SQL or raw errors. Unknown routes return 404. Exact-origin CORS; local diagnostics provide no authorization guarantee.

Timeouts: admitted connection acquisition 1000ms, server statement 1000ms, client query 1500ms, entire readiness operation 3000ms. A pool with four busy clients fails additional probes immediately with database_unavailable, rather than entering pg-pool's internal wait queue; this prevents replacement connections being started for expiring queued waiters. Deadline expiry destroys that operation's client. HTTP tests allow 4000ms scheduling tolerance. No retries per request; the next request checks current state. Pool errors are handled without driver diagnostics, failed clients are removed and shutdown closes resources. Invalid config exits before bind; unreachable DB keeps live=200 and ready=503.
