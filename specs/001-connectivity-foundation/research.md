## Current-schema-only release decisions

- Decision: explicit current-schema-only mode branches before the ordinary runner and only uses existing read-only status. Rationale: a runner that happens to apply0 violates the owner's no-runner constraint. Verify generated checksum/source/artifact manifest equality and full initialized/ordered/current history; the existing DB table stores names, not historical content hashes. No schema migration or second ledger is introduced.
- Decision: retain the predecessor root lock byte/inode-identical and claim exactly one successor through an exclusive fsynced receipt plus per-run lock. Rationale: avoids an unlink/replace race and preserves the historical unknown evidence; all ordinary releases remain fenced by the root lock. Reusing/deleting the claim or resuming create is rejected.
- Decision: strict immutable hashed run intent/create intent/ack/outcome records with file and parent-directory fsync. Mandatory adapter checkpoints make valid-ID persistence precede inspection. Rationale: `finally`-only reporting loses acknowledged identity on process death; synchronous acknowledgement persistence prevents advancing while a write is delayed or fails. No network exactly-once guarantee is claimed.
- Decision: read-only reconciliation consumes only verified durable identity and never calls trigger/migrations or rewrites original reports/locks. Missing/partial/tampered state fails closed; missing acknowledgement stays unknown. Runtime and provider enforcement remain separate evidence.
- Alternatives rejected: generic skip/force/unlock flags, a handwritten production wrapper, rerunning a nominal no-op migration, mutating old81d4 to terminal, silently relabeling oldea/0ed, new dependencies/DB audit tables, or a retry after uncertain create.

## Alternatives and decisions

- Plain pg plus node-pg-migrate is smaller than introducing an ORM for a schema-only connectivity check. Use explicit history table, single transaction, advisory lock and configured database client/timeouts. Verify version-9 option signatures against installed types before source acceptance; current website may document later main-branch options.
- Local official PostgreSQL is sufficient for this foundation. Full Supabase local stack/CLI would add unrelated Auth/Storage infrastructure. Hosted Supabase, Cloud Run and TLS/credential configuration remain later work; local success is not hosted success.
- Contract-first OpenAPI JSON avoids duplicated Nest Swagger DTO schemas. openapi-typescript emits types; later FE uses openapi-fetch. This increment proves generation in BE-owned output only, preserving FE lease.
- Database readiness requires both a fresh read-only query and expected migration history/schema. Socket liveness alone is insufficient. Explicit bounded connection/query/overall timers plus destruction of abandoned clients prevents indefinite checks and background resource growth.
