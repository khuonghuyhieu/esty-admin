## Retained initial research and proposal rationale

The original sections below preserve public source findings and initial alternatives. Their unresolved-policy wording is superseded by the current owner-approved baseline and engineering decisions above; remaining real setup/FE/release gates are not erased.

## R01 — Identity, profiles and membership

**Sources**: [Managing user data](https://supabase.com/docs/guides/auth/managing-user-data), [Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security).

Supabase owns `auth.users`; application tables may reference its primary key. Managed non-primary-key columns/constraints are not a stable application foreign-key contract. The guide's public profile table and signup-trigger example are examples, not required architecture; a failing signup trigger can block registration. User-editable metadata is not an authorization source. Deleting a user does not make an already-issued JWT cryptographically invalid before expiry.

**Recommendation**: Separate Auth UUID, global profile and workspace membership. Use explicit application admission rather than a signup trigger granting a role. Disable workspace membership rather than deleting Auth identity. Do not copy provider password/session internals into app tables. D01/D02/D06 govern policy, deletion behavior and DB privileges.

## R02 — JWT validation and signing-key rotation

**Sources**: [JWTs](https://supabase.com/docs/guides/auth/jwts), [Signing keys](https://supabase.com/docs/guides/auth/signing-keys).

Asymmetric project keys are discoverable at the configured issuer's `/.well-known/jwks.json`; a project using only symmetric signing may return no asymmetric keys. A decode is not verification. The JWT guide recommends a supported verification library or Supabase verification API, not homegrown cryptography. Expected issuer, audience, algorithm, expiry and identity/session claim requirements still need explicit application enforcement. Postgres `role: authenticated` is not the application's Owner/Member role.

Supabase documents a ten-minute edge JWKS cache and possible additional library caching. Key rotation/revocation is not instantaneous for an independently cached backend. For HS256, Supabase recommends online Auth-server verification rather than distributing the signing secret. No actual project's signing mode was checked.

**Recommendation**: Prefer approved asymmetric verification with a pinned library, fixed configured issuer/JWKS origin, an explicit algorithm allowlist, bounded cache/timeout and rotation tests. Reject attacker-supplied key URLs and malformed identity/session claims. D04 must resolve current signing mode and cache/revocation policy before implementation. Do not silently accept HS256, read/export a signing secret or rotate project keys.

## R03 — Session refresh and logout are not JWT revocation

**Sources**: [Sessions](https://supabase.com/docs/guides/auth/sessions), [Signing out](https://supabase.com/docs/guides/auth/signout), [Advanced SSR guide](https://supabase.com/docs/guides/auth/server-side/advanced-guide).

Supabase uses access JWTs and refresh tokens. Refresh tokens normally have single-use semantics with documented reuse exceptions, including the default ten-second reuse interval and the parent of the active refresh token. These exceptions support legitimate concurrency; they are not an application-wide lock or permission to retry arbitrary stale tokens.

Session JWTs contain `session_id`, corresponding to `auth.sessions`. Sign-out revokes the selected refresh sessions, but previously issued JWTs remain cryptographically valid until expiry. The session guide describes checking that `session_id` still exists for stronger enforcement. A row-existence check alone does not implement time-box or inactivity rules: expired session rows may remain until later cleanup. Paid session controls must not be assumed; documented time-box/inactivity/single-session controls are Pro-tier features. No plan upgrade is authorized.

The advanced SSR guide distinguishes `getClaims()` signature/expiry validation from online `getUser()` where session freshness matters. This plan does not label cached/local claim verification as a revocation check. The proposed NestJS boundary independently checks the matching Auth session row and current membership; exact read privileges and any additional lifetime policy remain D04/D06 gates.

JavaScript sign-out defaults to `global`; `local` ends the current session and `others` ends other sessions. Scope must be explicit. Membership disable is an app access decision, not a guarantee that Supabase stopped issuing that identity's tokens.

**Recommendation**: Current-session logout as the proposed ordinary action; strong server denial after confirmed revocation; no positive membership/session-existence cache across requests initially. After provider failure, clear local UI state without falsely reporting confirmed remote revocation. Password-reset/global-session consequences need D03 approval and actual later verification.

## R04 — SSR cookies, CSRF and concurrency

**Sources**: [Server-side Auth](https://supabase.com/docs/guides/auth/server-side), [Advanced SSR guide](https://supabase.com/docs/guides/auth/server-side/advanced-guide).

Supabase SSR uses cookies and PKCE. The current server-side guide labels `@supabase/ssr` beta; no dependency/version has been approved or installed here. Its standard browser/server client pattern requires browser access to user tokens and is not an HttpOnly-only session design. A server-only HttpOnly flow requires deliberately moving all Auth interactions behind a server adapter; setting HttpOnly on the standard browser SDK cookies would break refresh rather than provide a complete solution.

Supabase warns against caching responses that set session cookies and against module-scope user clients on reused server instances. Cookie/storage session data is not sufficient authorization evidence. The guide identifies stale SSR refresh tokens and browser recovery as real concurrency cases.

**Recommendation**: Review the documented SSR cookie lifecycle plus a strictly allowlisted business BFF first. Use request-scoped server clients, secure host-only cookies in HTTPS, appropriate SameSite behavior, private/no-store user responses, no authenticated ISR, explicit Origin/CSRF checks on cookie-authenticated mutations and constrained callbacks. Browser-readable user tokens carry XSS risk; the technical API key must nevertheless remain server-only. D04 must choose this tradeoff or a server-only HttpOnly adapter before any code. Require tab/SSR/refresh/logout races in later browser verification; do not claim an in-memory lock coordinates separate server instances.

## R05 — Invitations, recovery and real email delivery

**Sources**: [inviteUserByEmail](https://supabase.com/docs/reference/javascript/auth-admin-inviteuserbyemail), [generateLink](https://supabase.com/docs/reference/javascript/auth-admin-generatelink), [verifyOtp](https://supabase.com/docs/reference/javascript/auth-verifyotp), [resetPasswordForEmail](https://supabase.com/docs/reference/javascript/auth-resetpasswordforemail), [updateUser](https://supabase.com/docs/reference/javascript/auth-updateuser), [Password-based Auth](https://supabase.com/docs/guides/auth/passwords), [Custom SMTP](https://supabase.com/docs/guides/auth/auth-smtp).

`inviteUserByEmail` sends an Auth invitation. `generateLink` generates links/OTPs for delivery by a custom provider; generating a link is not delivery. Its documented types include invite, magiclink, recovery and email-change links. Recovery supports PKCE, and the authenticated update API owns password/email changes. Exact challenge type and callback behavior must match the selected flow; do not assume every invitation is a PKCE exchange or treat any returned token type as interchangeable.

Supabase's default SMTP is restricted to authorized team email addresses, has a low changeable rate limit (the inspected guide states two messages/hour) and no production delivery SLA. A production invitation/recovery journey therefore needs an explicitly chosen delivery arrangement. No sender address, legal identity, email-provider account, paid SMTP/trial or DNS change is implied. Local email capture later proves only local behavior.

**Recommendation**: Keep an app invitation as the membership offer, independent of provider authentication. Provider signup/invite/recovery links never grant an app role themselves. New and existing identities need distinct tested admission flows; no duplicate Auth-account creation or password reset disguised as a team invite. Persist delivery states including unknown; reconcile before resend. Email scanners must not accept membership by GET. D03 must settle email ownership, delivery, expiry, account setup and lost-owner recovery before implementation.

## R06 — Direct PostgreSQL is not automatic end-user RLS

**Sources**: [Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security), [Managing user data](https://supabase.com/docs/guides/auth/managing-user-data).

Grants and RLS are distinct checks. Tables in exposed schemas need explicit grants/RLS; defaults must not be assumed safe. Supabase's `service_role` bypasses RLS. A direct PostgreSQL connection does not automatically gain the browser user's identity merely because NestJS validated a JWT; owner/superuser/bypass privileges also affect enforcement.

**Recommendation**: Keep NestJS as the only app-data API, place app tables in a non-exposed schema, remove browser-role schema/table access and separate runtime from migration/operator privileges. Enforce capabilities and parameterized identity/workspace predicates in application transactions. Any RLS adopted is an explicit tested defense, not a claim that the existing direct connection enforces per-user policies. D06 must settle least privilege and narrow read-only Auth-session access. Do not create another Supabase migration history or modify managed Auth tables.
