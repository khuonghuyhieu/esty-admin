# Browser Session and Fixed-Origin BFF Contract

006's source/local contract, not another OpenAPI. The sole Nest schema remains [OpenAPI0.4.0](../../001-connectivity-foundation/contracts/openapi.json); its existing generated consumer is reused unchanged under the current T001–T014 grant. Integrated acceptance evidence belongs in [quickstart](../quickstart.md). The007/009 extension below remains planning only. Existing health/operator routes are never proxied through this BFF.

## Selected architecture

Use Next16 Node-runtime Route Handlers, native bounded fetch and Node's maintained AES-256-GCM primitive for purpose-bound cookie envelopes. No browser Supabase client, implicit token fragment flow, automatic SSR SDK refresh, frontend JWT verifier, new dependency, password/session database or new Nest business module. Nest retains maintained-library JWT verification and actual Auth-session/membership checks. Encryption protects transport secrets; a decrypted cookie alone never proves current admission.

Server-only configuration names documented in `apps/web/.env.example`: `APP_ORIGIN`, `APP_API_ORIGIN`, `APP_API_TECHNICAL_KEY`, `APP_AUTH_URL`, `APP_AUTH_API_KEY`, `APP_SESSION_COOKIE_KEY`, and `APP_SESSION_MODE=hosted|local` (default hosted). These are names, not existing values or permission to read owner files. App/API origins have no credentials/path/query/fragment; the fixed Auth base may retain its configured `/auth/v1` prefix. HTTPS is required except explicit local mode with separately approved literal-loopback fixtures. Auth issuer/project must match BE configuration. Do not trust request-supplied destinations, Host/Forwarded overrides, or NEXT_PUBLIC aliases for secrets. Missing/invalid configuration leaves protected app routes unavailable, never preview-authenticated; public routes remain independent.

Each server request gets its own identity/client context. No mutable module user state, cross-request authorization cache, static/ISR authenticated page or credential serialization into RSC/client props. Server pages read the raw Cookie value through Next's asynchronous `headers()` API so duplicate names remain detectable; a cookie map would collapse them. Cookie writes occur only in Route Handlers before response streaming. The same server-only caller may serve a page or BFF; do not HTTP-call the application's own BFF from an RSC.

## Cookie and generation invariants

- HTTPS names: `__Host-lovora-session` and `__Host-lovora-auth-context`; both HttpOnly, Secure, SameSite=Lax, Path=/, no Domain, browser-session cookies. Browser session restoration is not a promise of logout on browser close. Auth remains authoritative for lifetime/revocation.
- Explicit literal-loopback local mode uses `lovora-local-session` and `lovora-local-auth-context` with Secure=false and the same other attributes; hosted mode must reject that exception. Never infer local mode from an attacker-controlled Host header.
- Session plaintext contains only access token, refresh token, provider expiry hint, current generation and envelope version/purpose. Context contains random256-bit generation and CSRF nonce. Seal with a configured32-byte server key, fresh96-bit IV,128-bit authentication tag and authenticated purpose/version/origin/cookie-name binding. Reject wrong key/purpose/version, truncated/tampered values and duplicate cookies. Do not trust unverified JWT decoding for identity/role; expiry may only trigger an advisory refresh attempt.
- Bound each encoded cookie below3500 bytes; unsupported oversized provider sessions fail safely instead of exposing tokens, truncating or adding an unbounded chunk protocol. Test the actual local issued token size before acceptance. Do not return/log decrypted cookie contents or provider bodies.
- A session is usable only if its generation matches the current sealed context. Refresh/login success may write the session cookie but MUST NOT write the context cookie. Only context initialization, explicit begin and logout change context. A failed/stale refresh must not clear cookies or overwrite a newer context.
- Context generation is a browser response-order barrier, not a new revocation authority. Copies of credentials are denied after confirmed provider revocation by the existing BE check; unknown logout outcome never claims global revocation.

## Same-origin protocol and endpoints

All successful and failing responses use `Cache-Control: private, no-store`; add `Pragma: no-cache`, `Vary: Cookie`, safe request IDs, no token bodies and no upstream Set-Cookie passthrough. API routes return JSON errors, not login redirects. Unsupported framework-dispatched HTTP methods return405 with Allow and the same safe error metadata before configuration/provider work; HEAD follows HTTP's body-less semantics. Strict JSON Content-Type,16KiB request and64KiB upstream-response bounds; reject extra fields. Whole request budget8s with request-disconnect cancellation; individual Auth fetch at most1500ms and Nest fetch at most6500ms within the same total deadline. Redirect following is disabled. No automatic retry of login, refresh, logout or app writes.

| Browser operation | Input / effect | Allowed upstream / result |
|---|---|---|
| `GET /api/auth/context` | Same-origin fetch only (`Sec-Fetch-Site: same-origin`); initialize if absent; valid context is never rotated | No Auth/DB call. Return CSRF token and generation, neither an Auth credential. A single invalid/expired-key context is replaced only with a fresh signed-out context while clearing session/restricted cookies; never adopt old tokens. Duplicate cookies fail closed with browser-data reset guidance, not a retry loop. |
| `POST /api/auth/begin` | CSRF + exact Origin; current generation; no credentials. Explicit new sign-in attempt | Rotate generation/CSRF and clear old session synchronously, with no upstream call; return new CSRF/generation. This acknowledges the new browser auth attempt BEFORE credentials are submitted. |
| `POST /api/auth/login` | `{email,password,generation,returnTo?}`; matching context/CSRF | Auth `POST /token?grant_type=password`, then Nest `GET /v1/app/me`. Seal tokens under supplied current generation; never change context. Return admitted AppMe or an explicit authenticated/unadmitted state, not tokens. Auth failure writes no session. |
| `GET /api/app/me` | Current sealed session/context; no caller-supplied access token | Nest `GET /v1/app/me` only.200 body is generated AppMe, not a second copied DTO. No refresh/cookie mutation. |
| `POST /api/auth/refresh` | CSRF + current generation, no browser refresh-token field | Auth `POST /token?grant_type=refresh_token` using server cookie, then current `/me`. At most one explicit attempt; may replace session cookie under SAME generation only. |
| `POST /api/auth/logout` | CSRF + current generation | Rotate context and clear session on the returned response regardless of provider outcome; attempt Auth `POST /logout?scope=local` with the current server-held access token. Return `{localCleared:true,providerOutcome:"confirmed"|"unknown"}` only when the browser receives that response. No global scope and no hidden refresh/retry. An expired token/provider failure is unknown, not confirmed revocation. |

For every mutation (POST and later PATCH), require Origin exactly equal to configured APP_ORIGIN, matching Host, `Sec-Fetch-Site: same-origin`, and constant-time comparison of `X-CSRF-Token` with the nonce in the sealed context. Reject absent/null/foreign Origin and duplicate security headers. Login CSRF is covered, not just authenticated writes. CORS is not a replacement. `GET /api/auth/context` is readable only to the same origin; it cannot rotate an already valid context. Invalid-context reset is signed-out recovery only, not authentication; protected callers reject it until a new explicit sign-in.

BFF→Nest always reconstructs `Authorization: Bearer <server technical key>` and `X-App-Access-Token: <server user access token>`. Never forward browser Authorization/Cookie/Host/forwarding headers or accept a body token. Requests select a fixed enumerated operation, not an arbitrary catch-all proxy. Initially only GET me is enabled;007/008 add their exact operation tables through assigned FE ownership.

## Admission and safe error mapping

- Canonical app200/400/401/403/404/409/503 and `{code,requestId}` remain unchanged for app operations. Do not translate every401 into bad credentials.
- Nest technical guard401 `{status:"unauthorized"}` means BFF/server configuration failure: return safe503, never refresh-loop or prompt for another password. A malformed/unexpected upstream response is likewise safe503.
- Auth invalid credentials return generic401 without account existence; throttle returns bounded429/retry guidance without hidden retry; unavailable/timeout/malformed Auth returns503. These are BFF Auth outcomes, not new Nest/OpenAPI responses.
- App403 after successful Auth retains a server-held session for logout and future narrow invitation acceptance, but returns no admitted data. Do not distinguish unknown versus disabled membership by leaking an administrative record.
- BFF-only boundary errors are safe `{code,requestId}`:400 invalid_request,403 csrf_denied,405 invalid_request for unsupported methods,409 session_changed and503 upstream_unavailable/configuration failure. Never expose provider payloads, keys or recipient existence.

## Cross-tab, SSR and logout ordering

Use one origin-wide Web Lock for all context-changing/token-writing browser transitions: context initialization, begin→login, refresh and logout. Capture a client generation before each operation; re-read context after acquiring the lock. Never keep a module-global server lock or share a user client across warm server instances. BroadcastChannel carries only invalidation/generation notices, no user data/tokens. Required supported browsers must provide these primitives; unsupported browsers show a compatibility error instead of claiming safe session support.

Begin and login are distinct acknowledgements: only after begin's context cookie is received may the client submit credentials. This prevents a delayed credential result from changing the logout/new-attempt context. Keep the lock until response body/cookies are processed; on cancellation or tab close do not start a replacement refresh automatically. Explicit logout immediately invalidates rendered client state and pending reads; confirmation requires receiving the logout response. Network failure before that response shows sign-out unconfirmed, not a successful logout. Later session-cookie writes from an old generation are unusable against the current context; a stale overwrite may force fresh sign-in, never restore admission.

RSC/page guards and GET me NEVER refresh or write cookies. An expired-access page renders no protected data and directs to `/login?returnTo=<allowlisted path>` with a restoring state; the client performs one coordinated refresh and then reruns me. After successful auth/refresh, await the full response before `router.replace`/refresh; do not prefetch protected content while auth is unresolved. Every late data result is discarded unless its generation and current identity still match. A visibility/pageshow return revalidates me before revealing prior private UI; do not assume framework/back-forward cache is authorization.

A definitive refresh401 ends the unusable browser session through the existing client transition protocol, never through cookies on the failed refresh response. While still holding the same origin-wide Web Lock and client epoch, reread auth context. Only if its generation still matches the failed refresh request may the client POST existing begin with that current CSRF/generation; await its acknowledgement before showing signed out. A newer epoch must retain its newer intent; a different context generation conceals content and requires explicit checking without begin. Transient503, network uncertainty and stale failures do not clear cookies or trigger an automatic cleanup/retry. Reload/direct protected navigation after acknowledged cleanup must not retry the same invalid refresh.

Broadcast notices conceal and invalidate; they are not admission acknowledgements. Another tab offers an explicit Check session action rather than adopting a potentially late completion automatically. After an unconfirmed logout, automatic visibility/pageshow revalidation must not restore private content: require explicit retry, check or new sign-in. Even when the original JWT remains valid because the request never reached Auth, the UI preserves the user's pending sign-out intent.

Return destinations are exactly `/application`, `/settings`, `/settings/team`, default `/application`; no external/protocol-relative URLs, encoded traversal, arbitrary query or fragment.007 may add its validated invitation-UUID destination under its explicit contract extension. No callback/OAuth/PKCE/implicit flow is implemented by006.007/009 use the separately specified server token-hash email exchanges, not browser-readable access/refresh fragments.

## Shared email-challenge extension for007 and009

This is the single transport contract; dependent plans supply operation/UX bindings, not alternative cookies or authentication. These routes/helpers are future007/009 work, not extra006 implementation.

- Hosted challenge cookie: `__Host-lovora-auth-challenge`; restricted token cookie: `__Host-lovora-auth-restricted`. Local equivalents: `lovora-local-auth-challenge`, `lovora-local-auth-restricted`. Apply the session cookie's HttpOnly/Secure/Lax/Path/no-Domain/size/encryption rules. Both have Max-Age600 and a sealed absolute expiry enforced on each request; Auth may expire/revoke sooner. Never extend a challenge by rereading it.
- Challenge payload: random256-bit challengeId, exact purpose `invitation|recovery`, exact provider type (`invite|magiclink` for invitation; `recovery` for recovery), token hash, optional invitation UUID, creation/expiry and envelope version. Restricted payload: provider tokens/expiry hint, purpose/type/challengeId, current generation, optional invitation UUID and absolute expiry. No app roles or authoritative membership are stored here.
- Callback query size is at most4096 UTF-8 bytes; token_hash is1–1024 printable ASCII bytes without whitespace/control characters. Reject repeated/unknown parameters and missing or wrong literal type before setting a cookie. Invitation additionally requires exactly one canonical UUID; recovery accepts no invitation parameter. Bound the resulting sealed cookie as above. URL decoding never selects an upstream host/path or a return URL.
- Callback GET only captures a bounded typed hash in the challenge cookie and redirects303 to a clean page. It never verifies, sets an app session or admits membership. It does not rotate006 context. No third-party content/referrer/query logging on callbacks; deployment access-log query redaction remains a later verified hosting requirement. A late callback may replace a challenge and force restart, never establish authority.
- Same-origin context GET may additionally return safe challenge metadata (challengeId, purpose, provider type, invitation UUID and whether a valid restricted context exists), never hash/tokens. Under the same Web Lock, explicit user continue acknowledges begin, then verify submits only `{generation,challengeId}` plus006 Origin/CSRF headers. Begin clears ordinary/restricted tokens but preserves the captured challenge. Verify checks cookie purpose/type/expiry/ID, exchanges the server-held hash exactly once with Auth `POST /verify`, and writes only a generation-bound restricted cookie, never the context. Clear consumed challenge; an uncertain exchange is not blindly replayed. Provider one-use semantics, typed purpose and generation are all required.
- The invitation/recovery password handlers accept exactly `{password,generation}` under current CSRF/restricted context and call Auth `PUT /user`; password rules/errors come from the configured provider, not invented app storage. Tokens/passwords are never returned. All token-writing handlers hold the browser transition lock; late token cookies from a prior generation are unusable.
- Invitation restricted tokens authorize only new-invite password establishment, the matching explicit app acceptance, its subsequent current me confirmation, and local logout. No general team/settings/audit reads. Normal authenticated-but-unadmitted sessions may also use only the matching acceptance exception. Successful acceptance plus current me promotes to the ordinary session cookie under the SAME generation and clears restricted/challenge cookies; a403/503 does not fake promotion.
- Recovery restricted tokens authorize only password update and explicit global logout; they can NEVER promote directly to the ordinary session or call application operations. On known password-update success record a sealed `passwordChanged` phase in the restricted envelope; a separate completion POST attempts global logout without replaying the password write. After confirmed revocation rotate context/clear all auth cookies and require fresh006 password login. On uncertain revocation retain only the short-lived restricted completion context and show that distinction; if it expires, fresh sign-in and an explicitly acknowledged global-revocation retry are allowed only by009's completion handler, not silently by ordinary006 logout.
- Restricted cookie rewrites retain the original absolute expiry; password update/completion retry never extends it. A failed completion using the fresh ordinary-session fallback clears ordinary browser admission and reports global revocation unconfirmed; it does not invent a passwordChanged phase or mint a fresh restricted lifetime. The user may explicitly reauthenticate again or request a new recovery link. This safe fallback is not a guarantee that provider sessions were revoked.
- Ordinary begin/logout/invalid-context recovery clears restricted state; logout also clears the captured challenge. Every credential-changing transition invalidates rendered private state across tabs. Shared app reads may coordinate one explicit refresh followed by a fresh read; app writes are never automatically replayed after timeout/refresh.
- Return paths remain006's exact list plus007's `/auth/invitation/accept?invitation=<validated UUID>`. Recovery returns to `/login`, not an arbitrary URL. Separate callback paths: invitation `/auth/invitation` → `/auth/invitation/accept`; recovery `/auth/recovery/callback` → `/auth/recovery`. Hash/type validation is email-challenge verification, not an OAuth authorization-code/PKCE flow or a claim that default provider fragments work.

New-user invitation password establishment must be recorded in the sealed restricted phase before its UI enables accept. Existing-user magiclink skips that phase. This is onboarding sequencing, not a new Nest membership/password policy: the existing verified normal-session accept route retains its canonical behavior.

## Required proof, not planning assertions

Functional cases cover tampering/duplicate cookies, purpose/generation mismatch, CSRF/Origin denial before upstream work, technical401 mapping, byte/deadline bounds, no credential serialization and cancellation. Real browser cases cover two contexts, two tabs, concurrent SSR/refresh, logout during delayed refresh/read, stale success after a new begin, expired refresh and provider logout uncertainty. Replay the old JWT directly through approved local Nest after confirmed logout to prove actual session denial; a UI-only redirect is insufficient. No supported-cookie/race guarantee is considered implemented until these cases run against real local Auth and the production-built web surface.
